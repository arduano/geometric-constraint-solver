# M83 — versioned sketch lineage and deterministic rematerialization

Status: **planned; not implemented or accepted**. M83 is an architecture-and-proof milestone for
an optional host-side lineage companion. It does not replace the accepted M81 flat sketch product,
reactivate M82 computed Offset, or convert the complete workbench. Proposed ADR 0039 owns the
decision. Number 0038 is intentionally not reused because the archived, rejected M82 exploration
already used it.

## Product outcome

A sketch may be authored as an editable program of stable, ordered actions while
`SketchDocument` remains the flat, independently solved graph consumed by `geosolve-sketch`.
Lineage is the durable design source; the flat sketch is a deterministic materialization. Existing
computed-feature sidecars remain separate host composition in M83.

This distinction makes the requested workflows precise:

- placing a line creates one placement step;
- adding Horizontal creates a later constraint step referencing the line's logical output;
- dragging the accepted line rewrites the writable coordinates of the original placement step in
  one undoable lineage edit; it does not append a Move step;
- placing a shape and then Profile Offset creates separate placement and Offset steps;
- editing the source shape rewrites its placement step and rematerializes the unchanged Offset
  step; and
- deleting the Offset step removes every curve, point, scalar, source, constraint and dimension
  owned by that step, even after unrelated later steps were added.

Lineage is not a log of pointer events and is not the application undo stack. It is an editable
declarative program. The lineage session separately records accepted insert/rewrite/delete edits so
Undo can restore the previous program version and Redo can restore the same stable identities.

## Why existing state is insufficient

The current `SketchDocument` is deliberately a flat persistent graph. Its stable native IDs say
which point, curve or source exists, but not whether four lines came from a rectangle recipe,
which coordinates belong to a placement action, or which ordinary objects were generated by one
Offset operation.

Existing histories are also deliberately different:

- `SketchDocumentSession` and `RetainedEditorCoordinator` store accepted before/after snapshots;
- `ReplayAction` is an in-memory, revision-specific interaction transcript rather than durable
  declarative intent;
- `SketchOperationApplication::identity_changes` describes one transient proposal rather than a
  persistent feature step; and
- `ComputedFeatureDocument` is a useful sidecar precedent, but currently owns only computed
  feature intent and revision-local output, not the whole flat sketch program.

M83 must not infer a fictional authoring history from a flat document. A legacy document that can
be exported through supported canonical sketch v4 is represented honestly by one opaque
`SnapshotRoot` step. New actions may depend on typed outputs exposed by that root, but the internal
history of the imported snapshot remains unknown. Private draft-v5 bytes are never embedded or
promoted by canonical lineage v1. Existing draft-v5/workspace-v6 and computed-feature sidecars
remain outside this root until a later supported sketch-schema/workbench migration.

## Ownership and crate boundaries

M83 adds two pure safe-Rust companions:

### `geosolve-sketch-lineage`

This optional host-side crate owns:

- the versioned `LineageDocument` and canonical wire language;
- stable step IDs, stable typed output slots and materialized-ID reservations;
- dependency validation, resource limits, revisions, digests and exact compare-and-swap patches;
- deterministic scratch rematerialization through public sketch, operation and topology APIs;
- the bidirectional materialization/ownership map;
- direct-edit write-back into owning action fields; and
- retained intent, latest rebuild attempt, last complete accepted materialization and one
  lineage-level Undo/Redo history.

It may depend on `geosolve-sketch`, `geosolve-sketch-ops`, `geosolve-sketch-topology` and
`geosolve-geometry`. It must not depend on `geosolve-core`, `geosolve-linkage`,
`geosolve-sketch-features` or `geosolve-demo-web`, and none of the solver/domain crates may depend
on it.

The headless editor may translate completed authoring/direct-manipulation intent into lineage
patches in a later integration milestone; no browser event, selection heuristic or SVG state enters
the lineage language.

The crate owns no residual, Jacobian, rank policy, branch search, curve equation or independent
validation shortcut. It builds ordinary public transactions and accepts output only through the
existing solved and independently validated domain paths.

### `geosolve-sketch-lineage-wasm`

This is a separate DOM-free `cdylib`/`rlib` adapter. It depends on the lineage companion and the
pinned workspace-compatible `wasm-bindgen`, but has no `#[wasm_bindgen(start)]`, `web-sys`,
renderer, browser storage or dependency on the demo workbench. A browser CAD, Web Worker or Node
host can initialize it without installing GeoSolve's demo UI.

The raw ABI is a small versioned JSON-string boundary. It loads/creates a lineage document,
reconciles a complete program, applies exact-revision patches, exports canonical JSON and returns
discriminated evaluation results. Rust enums and internal coordinator types are not exported
directly through `JsValue`.

ADR 0026 continues to assign formula graphs, units, configurations, PDM identity, B-rep topology
and cross-system transactions to the embedding host. ADR 0039 narrowly permits a reusable optional
module for local sketch action lineage; it does not move host B-rep history into `geosolve-sketch`
or `geosolve-core`.

## Lineage document and action model

`LineageDocument` is a separately versioned, document-bound ordered dependency DAG. The stored
order is the deterministic evaluation order; references to later steps and cycles are invalid.
Each step contains:

- a stable monotonic `LineageStepId`;
- a unique durable host key used for TypeScript reconciliation, distinct from a mutable label;
- suppression and label metadata;
- one closed `LineageActionDefinition`;
- a typed output manifest with stable semantic slots; and
- the persistent native/source identity reservations for every object the step may materialize.

The document also owns the target sketch namespace and a monotonic materialized-identity
high-water above every live, suppressed, failed, deleted or history-retained reservation. A fresh
lineage begins from a new empty sketch namespace; a `SnapshotRoot` begins from the imported
document's exact high-water.

The conceptual action vocabulary has five owner categories:

1. snapshot roots for honest flat-document compatibility;
2. native geometry-placement recipes;
3. ordinary constraint and dimension additions;
4. native sketch operations such as M80 Profile Offset; and
5. a future extension point for computed-feature intent such as a `FilletSet`.

Category 5 is architectural vocabulary only in M83. Canonical lineage v1 contains no computed
feature action, stable feature-output map or new feature-ID reservation.

Branch, side, sweep, winding, traversal, geometry role, suppression and editable property changes
rewrite the action that owns them. They are not ambient solver choices or generic event steps.

M83 implements only the representative vertical slice needed to prove the architecture:

- `SnapshotRoot`;
- line and the existing M78 2-Point Aligned Rectangle recipe, including its four corners, four
  edges and recipe-intrinsic Horizontal/Vertical relations but no lock or dimension;
- an unrelated point placement used to prove late deletion stability;
- ordinary Horizontal constraint intent; and
- native topology-preserving Profile Offset over the admitted profile/chain slice.

The rectangle is offset as one authenticated closed face. This is enough to prove placement,
relation, multi-output shape, topology-sensitive operation, rewrite, deletion and compatibility
semantics. The remaining M78 recipe catalog, full relation and dimension catalog, computed Fillet
migration and other operation kinds are explicit follow-up work, not partially supported M83
behavior.

## Three identity layers

M83 keeps three identity scopes visibly separate:

1. **lineage identity** — stable step plus typed output slot; this is the durable reference used by
   later actions and TypeScript;
2. **materialized identity** — the current persistent sketch/source ID used by selection,
   attributes, rendering and public domain APIs; and
3. **accepted revision identity** — the exact independently validated materialization revision
   used for stale-work rejection.

A logical reference is `(LineageStepId, LineageOutputSlotId, kind)`. Fixed-cardinality recipes also
publish semantic roles such as `start`, `end`, `span`, `corner:top_right` and `edge:right`.
Profile Offset target-edge slots are keyed by the exact source logical edge, not by traversal index
or coordinate order.

`LineageMaterializationMap` is bidirectional and revision-stamped. It records:

- every logical output to its current native sketch/source identity;
- every materialized point/scalar leaf to the owning writable action field; and
- every step to all generated points, scalars, curves, contacts, sources, constraints, dimensions
  and hidden support state.

Computed feature intent and output are not M83 lineage outputs. They remain under ADR 0031 and
revision-local generated identity until a later milestone explicitly adds a feature action and
stable feature/corner mapping without pretending evaluated fragments have cross-revision identity.

## Stable materialized-ID gate

Full reconstruction with today's ordinary `SketchDocument::add_*` allocation can renumber
unrelated objects after an earlier insertion or deletion. M83 therefore starts with a blocking
identity seam before implementing the evaluator.

The accepted direction is explicit typed reservation, not hashing and not geometric matching:

- creation of a lineage step allocates and persists all presently known native/source IDs
  from the target document's monotonic high-water context;
- retaining a structurally valid step after a completed but invalid rebuild advances the
  lineage-owned materialized high-water; those IDs remain reserved and are never handed to a later
  step, while stale/cancelled/exhausted attempts retain neither the patch nor its reservations;
- a narrowly scoped public atomic `SketchMaterializationBatch` in `geosolve-sketch` carries the
  document namespace, expected base high-water, resulting merged high-water, typed reservations,
  semantic-source catalog ownership and curve-local spline span cursors;
- batch validation rejects a foreign namespace, stale base, wrong kind, duplicate against live or
  batched identity, dangling/cross-batch reference, invalid semantic-source reservation,
  non-monotonic span cursor or high-water regression before inserting anything;
- every accepted flat materialization carries a `next_id` at least as high as the lineage
  reservation high-water, including when a reserving step is suppressed or has been deleted;
- an operation step receives a disposable step-scoped allocation context backed by its reservation
  set, and publication rejects if the proposal consumes a different identity kind, count or order;
- rebuilding reuses the reservation, so inserting or deleting an earlier step cannot renumber an
  unrelated later output;
- deleting a step retires its identities without reuse; Undo restores the same reservations and
  Redo removes the same objects again; and
- variable-cardinality future operations allocate new child slots and reservations only through
  an explicit old-to-new/retired/split mapping.

If this seam cannot preserve identity without weakening document validation or allocator
monotonicity, M83 stops. Revision-local remapping is not an acceptable silent fallback for this
milestone because it would break host attributes, selection and durable TypeScript handles.

## Deterministic materialization

The evaluator validates the complete lineage structure before geometry work, then rebuilds on
scratch state in deterministic step order. Each accepted prefix supplies the exact fresh input for
the next step. Sequential evaluation is deliberate: Profile Offset and later topology-sensitive
actions require an independently accepted upstream sketch and authenticated topology snapshot.

The evaluator may keep digest-keyed prefix checkpoints as disposable performance caches, but a
cache is never authoritative or required for persistence. Cold and warm rebuilds must produce the
same lineage-output mapping, persistent materialized IDs, branch state and accepted domain result.

Every attempt carries lineage revision/digest, immutable host-input stamps, work limits and
cancellation state. Publication uses exact compare-and-swap. Cancelled, exhausted, stale,
structurally invalid, unsolved or independently rejected work publishes no partial lineage result
and consumes no live flat-document allocator state. A completed invalid program edit that is
retained may advance only the lineage reservation high-water described above.

`LineageSession` mirrors the retained M34 authority split:

- retained lineage intent;
- latest rebuild attempt with per-step `Current`, `Suppressed`, `Blocked` or `Failed` evidence; and
- the last complete independently accepted materialization.

A downstream Offset failure after a source rewrite retains the previous complete accepted scene.
The failed attempt may expose diagnostic/provisional prefix evidence, but it cannot masquerade as
the current authoritative materialization or leak stale target geometry.

## Dynamic editing and history rewrite

Projected editing is a stricter all-or-nothing reconciliation API. It begins only when retained
lineage revision/digest exactly equals the source lineage of the accepted materialization and its
reverse ownership map. On release:

1. collect the accepted point/scalar values changed by the ordinary solver projection;
2. map every action-owned continuous leaf needed for deterministic replay back to its writable
   placement fields;
3. preserve all later constraints, dimensions, operations and explicit branch fields unchanged;
4. apply one expected-revision `RewriteSteps` transaction containing one or more owner-step
   replacements atomically;
5. cold-rematerialize the proposed lineage; and
6. independently prove that the result reproduces the accepted projected state before publishing
   one lineage history entry.

Failure of step write-back, cold reproduction or downstream rebuild rejects the complete projected
reconciliation: it retains neither rewritten lineage nor history and keeps the prior accepted
materialization. This is intentionally stricter than an explicit program edit.

The write-back is action-specific. A line owns start/end coordinates; a centre-based recipe owns
its centre and authoring parameters rather than an arbitrary browser point list. One solver
projection may legitimately move fields owned by several placement steps, so all affected owners
must enter the same lineage transaction or none may change. No inverse rule may infer or switch
side, sweep, winding, neighborhood or traversal from coordinates.

Profile Offset target coordinates are never stored as free placement values. The Offset step owns
distance/direction/branch intent and the source placement owns its writable geometry. Editing a
source rematerializes the target. A future target-handle interaction must explicitly choose an
inverse owner such as source placement or Offset distance; it cannot persist sampled derived
coordinates.

The lineage mutation vocabulary is small: insert, rewrite, delete, suppress/unsuppress, reorder
where dependencies permit, and explicit rebind. Every patch names the expected document revision
and digest. A malformed, stale, wrong-kind or otherwise structurally rejected patch adds no history
entry and clears no redo entry. A structurally valid program rewrite is retained and enters lineage
history exactly once even when a downstream rebuild fails; its accepted-materialization pointer
does not advance, and Undo returns to the preceding valid program/materialization. There is one
application Undo stack at the lineage layer; scratch sketch/editor histories are not nested
user-visible histories.

While retained lineage is ahead of or invalid relative to its last accepted materialization,
projected reconciliation is unavailable: the old accepted reverse map cannot rewrite the newer
program. Undo or an explicit program repair must first produce a matching accepted materialization.
M83 performs no proximity or implicit cross-revision rebase.

Deleting a step with live downstream dependents returns a typed `HasDependents` result unless the
caller supplies a separately explicit cascade/rebind transaction. M83 proves deletion only with
later unrelated steps and does not silently cascade or retarget dependents.

## Topological naming seam

M83 solves naming only for the admitted sketch-lineage outputs:

- fixed-cardinality outputs retain semantic slots;
- same-cardinality Profile Offset outputs retain a source-keyed target slot;
- operation proposals must provide explicit retained/replaced/proposed identity evidence; and
- a missing, ambiguous, split or retired output blocks its dependent until an explicit mapping or
  rebind is supplied.

Coordinate equality, nearest geometry, tessellation order and source insertion order never repair
identity. The API reserves an explicit identity-delta vocabulary for later variable-cardinality
operations, but M83 does not claim trimming, topology-changing Offset, arbitrary computed-fragment
naming or the host B-rep topological naming problem.

## TypeScript/OpenSCAD-style boundary

The supported TypeScript shape is a data-only builder over the DOM-free WASM engine:

```ts
const sketch = new SketchProgram("demo");

const base = sketch.line("base", [0, 0], [10, 2]);
sketch.horizontal("base-horizontal", base.span);
sketch.offsetChain("upper", [base.span], {
  distance: 2,
  side: "left",
});

const result = engine.reconcile(sketch.toJSON());
```

The explicit keys are durable reconciliation identity; call-order-only numbering is not stable
enough for source edits. Branded `PointRef`, `CurveRef`, `SpanRef` and related handles make
wrong-kind references compile-time errors where possible, while Rust repeats all validation at the
trust boundary. IDs, revisions and high-water values cross JSON as opaque strings rather than
lossy JavaScript numbers.

TypeScript assembles finite versioned DTOs only. It contains no curve equation, offset algorithm,
constraint lowering, branch heuristic or success validation. Rust never calls JavaScript while
lowering, solving or validating.

Arbitrary user TypeScript source is not safely rewritable by the geometry engine. Two honest host
modes remain possible:

- an interactive lineage document is authoritative and may be exported as canonical generated
  TypeScript; or
- a TypeScript program is authoritative and direct manipulation returns a typed step/field patch
  for the host to apply to parameters, a structured AST or an override layer before rerunning.

M83 proves canonical Rust/JSON/WASM/TypeScript shape parity and a compile-checked example. It does
not publish an npm package, promise source-to-source rewriting or add a script editor to the demo.

## Implementation sequence

1. Accept ADR 0039 and freeze the M81 product baseline, current Cargo graph, canonical sketch
   fixtures and 271-row authoring/scene golden without re-blessing output.
2. Add the typed explicit-ID reservation/materialization seam and prove unrelated insertion,
   deletion, suppression, Undo/Redo and cold rebuild preserve IDs and allocator high-water.
3. Add the lineage model, validation, canonical v1 wire format, resource limits, `SnapshotRoot`,
   typed output refs, ownership map and exact-revision patches.
4. Add scratch sequential evaluation and the representative placement, Horizontal and native
   Profile Offset action slice using only public owning-domain APIs.
5. Add accepted direct-edit reconciliation, source-step rewrite, late Offset deletion and the
   retained failed-rebuild authority path.
6. Add the DOM-free WASM adapter and data-only TypeScript builder/example with explicit keys and
   branded handles.
7. Run focused native/WASM/parity/persistence/concurrency tests, the unchanged golden authority
   and the complete clean release gate. Record technical review rather than claiming a polished
   workbench migration or Pages feature.

## Acceptance scenarios

### M83-L1 — line, constraint and rewrite

Create `PlaceLine(base)`, then `Horizontal(base.span)`. Project an accepted drag that translates
the constrained line. Exactly the placement fields change; no Move step appears; the Horizontal
step and all step/output/materialized identities remain stable. Undo and Redo restore the two
program versions and cold reload is deterministic.

### M83-L2 — shape, Offset and source rewrite

Create the admitted 2-Point Aligned Rectangle, apply native Profile Offset to its closed face, then
rewrite the source placement through an accepted drag. The rectangle's intrinsic relations and the
Offset action bytes/branch intent remain unchanged, its source-keyed target outputs retain their
identities, and the rematerialized association passes the existing exact offset, topology and
independent-validation gates.

### M83-L3 — late deletion owns the whole Offset

After L2, add an unrelated point action and constraint-free placement edit. Delete only the Offset
step. Every object in the Offset ownership set disappears; no target curve, hidden scalar,
connectivity source, constraint or dimension survives. Source and unrelated outputs retain exact
identities. Undo restores the same Offset step and materialized IDs.

### M83-L4 — failed downstream rebuild retains authority

Use an explicit numeric `RewriteSteps` program edit—not projected drag reconciliation—to rewrite
the source into a state that makes the unchanged Offset invalid. The retained lineage intent and
per-step failure identify the Offset; the complete prior accepted materialization, accepted
revision and live materialized allocator high-water remain authoritative. The valid program edit
advances lineage history exactly once without advancing accepted-materialization history. No
partial target or stale proposal is published; projected editing is unavailable against the old
reverse map, and Undo recovers exactly.

### M83-L5 — identity and dependency safety

Insertion before an unrelated step, suppression, rebuild and deletion never renumber its logical
or materialized IDs. Wrong-kind, unknown, forward, cyclic and cross-document references reject.
Deleting a step with live dependents returns `HasDependents`; no proximity rebind or implicit
cascade occurs.

### M83-L6 — legacy truthfulness

Wrap representative supported canonical-v4 flat sketches in `SnapshotRoot`, round-trip canonical
lineage JSON and append a new supported lineage action. The exact imported native IDs survive, no
fictional recipe history is synthesized, and malformed/oversized roots reject atomically. A
private draft-v5 payload receives a typed unsupported result and is never embedded, normalized or
promoted by lineage v1.

### M83-L7 — persistence, work and publication

Canonical JSON round-trips byte-for-byte with stable digest and allocator state. Stale CAS,
pre-cancellation, deterministic work exhaustion, non-finite inputs, invalid output mappings and
ID exhaustion retain the previous accepted materialization and consume no live reservations.
Cold and cached rebuilds agree.

### M83-L8 — Rust/WASM/TypeScript parity

Equivalent Rust and TypeScript builders produce the same canonical lineage payload. Native and
DOM-free WASM evaluation return the same discriminated status, logical-output mapping,
materialized document digest and independent hard-validity evidence. The TypeScript example is
compile-checked, contains no geometry logic and can initialize without a DOM.

## Qualification and closeout

- Every public lineage and WASM DTO has deterministic ordering, bounded decoding, explicit version
  and structured errors.
- Focused owner tests cover L1-L8, including exact step ownership and all rejection sentinels.
- Existing Profile Offset, operations, topology, feature, editor and persistence suites pass
  unchanged. M83 adds no residual, so it adds no Jacobian row; all reused equations retain their
  existing finite-difference and audit gates.
- The reviewed 271-row authoring/scene golden remains unchanged. Any systemic golden expansion is
  separately reviewed under the repository defect-hardening workflow rather than auto-blessed.
- Formatting, diff hygiene, warnings-denied workspace Clippy/Rustdoc, locked all-feature tests,
  native/WASM parity, benchmark compilation, licence/package checks, demo Trunk build and the
  complete release gate pass from committed source.
- M83 closes only after a focused architecture/API review confirms the identity seam, lineage
  versus Undo distinction, failure authority and TypeScript boundary. Because the ordinary
  workbench is not migrated, M83 does not require a new Pages deployment or claim hands-on feature
  UAT.

## Explicit deferrals

M83 does not convert all 25 M78 authoring variants, the full relation/dimension catalog, every
operation, computed Fillet intent, existing sample library or ordinary workbench persistence to
lineage. It adds no topology-changing/computed Offset, trimming history, arbitrary-curve Offset,
computed-on-computed chaining, stable generated-fragment naming, B-rep/PDM topological naming,
formula language, unit system, configuration engine, collaboration/merge protocol, npm release,
TypeScript source rewriter, browser script editor or mobile UI.

Those surfaces follow only after the stable-ID, rewrite, deletion, failure and TS-boundary proofs
are accepted.
